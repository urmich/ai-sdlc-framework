## 1. Approach and limits

Keep validation short: observe this framework's own development and run small
deterministic checks over files, Git metadata, and CLI contracts. No separate
product, simulated development project, scripted AI sessions, model-judged
scoring, or benchmark harness is created.

The approved approach maps every requirement to checkpoints without exhaustive
per-DoD-condition evaluation. That limited depth is a project-specific exception
under FR-006, not a weaker default for projects using the framework. Manual
observation is deliberately lightweight; automate structural assertions where
they are actually deterministic.

FR-054 additionally maps every acceptance criterion explicitly in section 3.1.
Its focused repository checks and external observations remain separate. This
The subsequent FR-054 Technical Design authorization does not authorize
implementation, GitHub-setting changes, publication, or a consumer exception request.

Following the methodology before the framework is installed is useful design
feedback, not proof its eventual implementation works. Post-installation
observations and automated results are recorded separately from that feedback.
Coverage below means planned coverage, never that every requirement has passed.

## 2. Execution and evidence

Observe T-01..T-13 when their situations arise during this repository's work.
Do not invent a project, perform a real deployment, or manufacture an unrelated
bug just to exercise a checkpoint. Record unobserved behavior as `NotRun`.

T-14..T-51 and T-53..T-57 use isolated repository-local fixture trees, small
event/hook-payload fixtures, and minimal Git repositories containing only
metadata/sample artifacts.
These are component fixtures, not simulated product work. They require no LLM
calls, cloud resources, live credentials, or modification of this checkout's
runtime state. Persistence failures are injected at specific steps rather than
using random kill timing. Never delete a live checkpoint for a test.
Deployment-flow cases use recorded-shape CI/CD provider response fixtures and a fake clock:
no actual pipeline runs, cloud deployments, or 60-second sleeps are needed.
PR cases use provider-response fixtures; no actual PR, review vote, or merge
is created by these tests. The formal candidate-review case uses the supported
Copilot CLI `/review` result contract or a deterministic fixture of that result;
it does not create a second review agent or an AI-evaluation benchmark.

T-52, T-58, and T-59 require separately authorized external observations.
Local fixtures establish only the expected decision and evidence contracts;
they cannot establish that GitHub settings are enabled or enforced, scheduled
jobs ran, reporting channels are enabled/reachable, or public provenance verifies. T-53..T-59
are newly designed and all remain `NotRun`; documentation checks do not execute
these scenarios. An unavailable capability or access path retains `NotRun`
with a separate `Blocked` diagnostic and reason. An observed mismatch is
`Failed`, not a capability limitation. A local negative-case test can pass by
correctly rejecting a fixture without making the represented external control
Passed. No scenario submits real secrets, weakens repository protections, or
manufactures an external approval.

For an executed checkpoint, record outcome, artifact/revision, environment,
validation cycle, test-specification identity, and a short evidence reference.
Keep logs outside this table. Every test's Status is `NotRun`, `Passed`, or
`Failed`, as required by FR-015. `NotRun` means no conclusive current-cycle
result is available; running activity, blockers, and unverified outcomes must be
stated separately rather than hidden behind that value.
Implementation readiness is also separate. The statuses below reflect actual
framework observations and deterministic executions for the current candidate.
Update them only from actual execution/user results; a new validation cycle resets
them to `NotRun` without deleting historical evidence.
Only local tests rerun automatically after a fix. DEV tests stay `NotRun` with
an awaiting-authorization detail until the user authorizes the separate DEV step.
Conformance verdicts and process exit codes are separate and tested by T-21.
In this framework's own plan, manual checkpoints are user observations and most
automated/semi-automated checks are agent/runner-owned. T-35 is a user-invoked
automated `/review` command. STAGING ownership and host restrictions are tested as
contracts, not by accessing a secured environment.

## 5. Cost and design maintenance

The available development window is roughly one to one and a half days.
Deterministic cases stay small and run locally; manual review accompanies work
already happening. No AI evaluation suite is planned.

T-16..T-46 cover the design's concrete failure paths, deployment/PR requirements,
candidate Review, installable package CI, and focused engineering instructions.
The one-minute cadence is tested with virtual time, not long-running AI sessions.
T-53..T-57 likewise use small deterministic fixtures and virtual time for
exception expiry, evidence freshness, and scheduled vulnerability discovery.
T-58..T-59 remain separately authorized observations, not an expensive campaign
or authority to implement code or modify external controls during Technical Design.
These are focused contract cases, not extra product scope. Add or refine a short
case when implementation or observation exposes a new defect. Do not turn these
checkpoints into a project simulation or silently
reduce the required behavior to obtain green results.
